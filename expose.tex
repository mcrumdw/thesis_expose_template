\section{Introduction and Motivation}

In-car voice assistants are moving from fixed command grammars to agents built on large language models (LLMs) that accept free-form requests \cite{Alvarez26Do}.
Once such an agent can also call vehicle functions, a spoken sentence becomes an action in the car, such as a changed temperature, a new route or an opened window \cite{Kirmayr26CAR}.
This promises an assistant that needs no learned vocabulary, but it raises a safety question: what happens when the agent gets it wrong while the driver is driving.
Every misunderstanding costs repair dialogue, and effortful voice dialogues go together with frustration and less stable lane keeping \cite{Liu26Affective}.

Current evidence answers this question only in parts.
User studies show that drivers prefer an LLM agent to a scripted one \cite{Choe26ChatGPT}.
Benchmarks show that tool-using agents still fail on ambiguous requests and on requests for functions the car does not have \cite{Kirmayr26CAR}.
Neither tells how close an LLM assistant comes to a competent human who has the same vehicle functions, which is the reference point a designer actually aims for.
The evidence also comes almost entirely from drivers who do not speak German, although tool calling is known to degrade outside English \cite{Luo26Lost}.

The thesis therefore compares a tool-using LLM assistant with a human Wizard-of-Oz (WoZ) assistant who has the same tools and instructions, with German-speaking drivers in a driving simulator at Technische Hochschule Ingolstadt (THI).
It covers one LLM, the German language, manual driving and in-cabin tasks for comfort, media, phone and navigation; it does not compare several LLMs, contrast German with English, test real traffic or automated driving, or design a new assistant.

\section{Problem Statement and Research Questions}

It is unknown how far a tool-using LLM in-car assistant falls short of a competent human assistant, and on which requests.
Existing evaluations compare the LLM with a scripted agent, with no agent, or with a simulated user \cite{Choe26ChatGPT,Kirmayr26CAR}.
They therefore cannot separate failures of the agent from tasks that are hard for anyone.
German-speaking drivers have not been studied with such an agent, so it is also unknown whether German requests add failures of their own.
Three research questions guide the work:

\begin{longtable}{p{0.3cm} p{0.8cm} p{12.7cm} p{0.5cm}}
    & \textbf{RQ1} & To what extent does a tool-using LLM assistant differ from a human assistant with the same tools in task success and dialogue efficiency when German-speaking drivers make in-cabin requests while driving? & \\
    & & & \\
    & \textbf{RQ2} & How does the type of assistant (LLM or human) affect drivers' lane keeping, workload, perceived usability and trust? & \\
    & & & \\
    & \textbf{RQ3} & Which request types and German-language features characterise the tasks that the LLM assistant fails but the human assistant completes? & \\
\end{longtable}
\addtocounter{table}{-1}

Each question is answered with measures defined in Section~5 and within one study session per participant.

\section{Objectives}

The primary objective is to \textbf{compare} a tool-using LLM assistant with a human assistant on identical German in-cabin tasks, using the human condition as the reference point for what the LLM could achieve.
Five secondary objectives support it:

\begin{enumerate}
    \item \textbf{Design} a German task set of 24 in-cabin tasks in two matched sets of 12, with ground-truth tool calls for clear, two-step, clarification-needed, missing-function and German-feature requests.
    \item \textbf{Specify} the human condition as a reproducible instrument through a written wizard protocol, wizard training and a pilot.
    \item \textbf{Conduct} a within-subject driving-simulator study with 36 German-speaking drivers.
    \item \textbf{Analyse} task success, dialogue efficiency, driving behaviour and questionnaire data, and classify every LLM failure on a task the human completed.
    \item \textbf{Release} the pseudonymised session data, the task set and the wizard protocol to the WorlDrive corpus so that later studies can reuse the human baseline.
\end{enumerate}

\section{Related Work}

The search covered the ACM Digital Library, IEEE Xplore, Google Scholar and arXiv for 2015--2026, combining in-vehicle voice assistant, LLM agent and tool calling with Wizard of Oz, human baseline and driver workload.
Backward snowballing started from the supervisor's PromptDrive paper \cite{Alvarez26Do}.
Only peer-reviewed sources were retained.

\subsection{LLM Assistants with Real Drivers}

LLM-based agents can make driving steadier and are preferred over scripted ones: in a motion-based simulator, a ChatGPT-based agent led to more stable driving than a scripted agent or no agent, and 40 drivers rated it higher in competence, affective trust and preference than the scripted agent~\cite{Choe26ChatGPT}.
Effortful voice dialogues carry a cost while driving: navigation tasks that needed more turns and longer completion times went with frustration, lower perceived control and less stable lane keeping and speed regulation~\cite{Liu26Affective}.
First data on German command phrasing point to a higher burden: when drivers in Germany and Mexico spoke single commands in the PromptDrive pilot, with no agent responding, the seven German-language sessions reported the highest workload of all cells, though only descriptively~\cite{Alvarez26Do}.

Together these studies show that LLM assistants are preferred and that dialogue effort matters for driving.
They share three limits.
The comparator is a scripted system or none, so none says how good an LLM assistant is in absolute terms.
None scores whether the assistant completed the driver's request against ground-truth actions.
And apart from the seven PromptDrive sessions, none involved German-speaking drivers.

\subsection{Tool-Using Agents and Language}

Even frontier LLM agents still fail on in-car requests that call for judgement: with 58 interconnected vehicle tools, they completed fewer than half of the tasks that need a clarifying question consistently, and they often acted on requests for functions the car does not have~\cite{Kirmayr26CAR}.
These are the two task types this thesis adopts.
Scored against ground-truth actions, the benchmark measures what the user studies leave out, but its users are LLM-simulated, its language is English and it involves no driving.

Tool calling also degrades outside English: in Chinese, Hindi and Igbo, models fail even when they understand the intent and pick the right tool, mostly because they fill parameters with words in the user's language where the tool expects fixed English values~\cite{Luo26Lost}.
No inference-time fix fully restored English-level performance.
German was not tested, and neither was a car.

\subsection{The Human as Reference}

The Wizard-of-Oz method lets a hidden human play the system, which makes it the natural way to obtain a human reference.
An LLM can already seem as socially intelligent as a human operator: in a brainstorming task, a robot driven by GPT-4 was rated as socially intelligent as the same robot driven by a wizard, although the 27 participants reliably identified which one the human controlled~\cite{Vrins24Wizard}.
That comparison covered perception only; the robot had no tools to operate.
Published Wizard-of-Oz studies often omit what a reader needs to judge the human condition: few of 54 reviewed experiments reported how the wizard was trained, which errors the wizard made, or whether participants noticed that a human was in control~\cite{Riek12Wizard}.
Following the reporting guidelines from that review, this thesis documents the wizard's training and protocol, records who played the wizard in each session, and checks at debriefing whether participants recognised the human, so that the human condition can be repeated.

\subsection{Theoretical Lens: Trust in Automation}

Trust in automation is an attitude formed from beliefs about the system, chiefly its reliability and competence and its understandability and predictability~\cite{Koerber19Trust}.
In the validation of this model, an unreliable automated driving system received lower trust ratings, and trust predicted reliance in a simulator study.
The thesis uses Körber's model as its lens: failed tasks and unexpected replies should lower the perceived reliability and predictability of the LLM assistant and therefore trust.
The lens also shapes the measurement: trust is captured after each block with a multi-item scale that also covers the willingness to rely on the assistant, and the failure analysis of RQ3 is read as the source of perceived unreliability.

\subsection{The Gap}

User studies have real drivers but no human reference and no ground truth.
Benchmarks have ground truth but simulated users, English and no driving.
The Wizard-of-Oz literature offers the method but has not used it to benchmark a tool-using assistant in the car.
No study compares a tool-using LLM assistant with a human assistant who has the same tools, with German-speaking drivers, on task success, driving and trust at once.
RQ1 addresses task success and efficiency, RQ2 driving and experience, and RQ3 uses the human condition to separate failures of the LLM from hard tasks.

\section{Methodology}

The thesis uses a within-subject controlled experiment in which every participant completes matched in-cabin tasks once with the LLM assistant and once with the human assistant.
The within-subject form removes differences in driving skill, language and attitude towards assistants between people.
Four hypotheses follow from the research questions and the lens; RQ3 is exploratory.

\begin{itemize}
    \item \textbf{H1} (RQ1): The task success rate is lower with the LLM assistant than with the human assistant, and the gap is largest for clarification-needed, missing-function and German-feature tasks.
    \item \textbf{H2} (RQ1): Completed tasks need more dialogue turns and more time with the LLM assistant.
    \item \textbf{H3} (RQ2): Lane keeping during tasks is less stable with the LLM assistant (higher SDLP relative to the pre-task baseline).
    \item \textbf{H4} (RQ2): After the LLM block, workload is higher and trust and perceived usability are lower than after the human block.
\end{itemize}

\subsection{Use Case Definition}

The object of study is the in-cabin voice assistant of a passenger car, run on WorlDrive, the driving-simulator platform of the Human-Centered Intelligent Systems Lab at THI.
WorlDrive records driving telemetry at 10\,Hz and lets the participant talk to an assistant that acts on 44 vehicle functions for climate, openings, lights, media, phone, navigation and vehicle information.
The assistant seat is filled either by an LLM agent or by a human wizard who works in the WoZ console in a second room.
Both receive the same system prompt and the same tools, and both reply through the same text-to-speech (TTS) voice.
This equality is what makes the human a fair reference rather than a differently briefed assistant.
Each task has an initial cabin state, ground-truth tool calls and completion rules, from which the platform scores success automatically.

The LLM is one current model with tool calling and strong German performance; its version, system prompt and temperature are fixed before the pilot and not changed afterwards.

Sessions take place in the lab with manual driving on a rural road with light traffic.
Drivers speak through a push-to-talk button, because open-microphone voice detection failed in noisy settings in the PromptDrive pilot \cite{Alvarez26Do}.

Participants are 36 licensed drivers aged 18 or older whose first language is German or who rate their German at CEFR level C1 or higher.
People with a history of simulator sickness are excluded at screening.
Recruitment runs through THI mailing lists and notices in Ingolstadt.

\subsection{Independent Variables}

The manipulated variable is the \textbf{type of assistant}, with two levels, \emph{LLM agent} and \emph{human wizard}, varied within subjects.
Two matched task sets (A and B) of 12 tasks each, with equal composition, ensure that no participant meets the same task twice.
Condition order and the pairing of task set with condition are both counterbalanced, giving four sequences with nine participants each.
Participants are assigned to sequences by a pre-generated random list.

\paragraph{Who plays the wizard.}
The wizards are the participants themselves, linked in a chain agreed with the supervisor: after driving both blocks and being debriefed, each participant plays the wizard for the next participant.
Every wizard receives the same scripted training, a rule card and one practice task, and agrees to keep the human condition confidential before taking the console.
The first driver of each chain has no predecessor, so a stand-in plays the wizard there and wherever a cancellation breaks the chain; whether the stand-in is the study assistant, the author or a separately recruited person is still to be decided, and these sessions are flagged in the data.
Almost every participant thus serves twice, once as driver and once as wizard, so 36 participants remain enough.
Wizards never meet the driver they assist, and apart from the stand-ins none of them knows the hypotheses.
In return, the human condition represents an ordinary German-speaking co-driver after a short training rather than an expert operator, and wizard skill varies between sessions.
Following the reporting guidelines for Wizard-of-Oz studies, the thesis states who the wizards were, how they were trained and what they knew~\cite{Riek12Wizard}.

The LLM receives only the speech-recognition transcript, while the wizard can also play the driver's audio in the console.

WorlDrive provides the items in English; the German wording is translated and reviewed before the pilot.

\subsection{Procedure / Research Steps}

Each participant attends one visit of up to two hours in two parts.
In Part~A (about 60\,min), the participant drives:

\begin{enumerate}
    \item Welcome, consent, demographics and screening, all entered in WorlDrive on the simulator computer (9\,min).
    \item Seat adjustment and practice drive without the assistant (7\,min).
    \item Block~1 with the first assistant: 12 tasks spaced along the route, each shown as a goal on the head-up display (12\,min).
    \item NASA-TLX, UEQ-S and trust scale in WorlDrive (4\,min).
    \item Block~2 with the second assistant (12\,min), followed by the same questionnaires and a simulator-sickness rating (4\,min).
    \item Short interview on both assistants, used to interpret the RQ2 and RQ3 results (5\,min).
    \item Manipulation check, first as an open question and then as a direct one, disclosure that one assistant was a human, and the invitation to play the wizard (6\,min).
\end{enumerate}

In Part~B, the participant gives a second consent, is trained on the console with a fixed script and one practice task (10\,min), and plays the wizard during the human block of the next participant (12\,min).
Depending on that participant's sequence, Part~B takes 36 or 52 minutes; the last participant of each day leaves after Part~A.
Participants are told they will test two versions of the assistant, and the wizard works in a second room.
The experimenter is not blind to the condition, which the protocol limits by fixed instructions.
The author leads the sessions, interviews and debriefings, and a German-speaking student assistant runs the WorlDrive backend and the wizard room.
A pilot with three to four people checks timing, whether 12 tasks fit into one block, task scoring and wizard consistency before data collection.

Data collection starts after approval by the ethics committee.
Participants give informed consent, may stop at any time and may withdraw their data after the disclosure; all data are stored under pseudonymous session codes in line with the General Data Protection Regulation (GDPR).

\subsection{Statistical Analysis}

Task success rates are compared between conditions with a paired $t$-test, or a Wilcoxon signed-rank test if the differences are not approximately normal (RQ1).
A mixed-effects logistic regression on single task outcomes, with participant and task as random effects and wizard as a random effect within the human condition, tests whether the gap depends on task type as H1 predicts (RQ1).
Dialogue turns and time in completed tasks are compared with paired tests on per-participant means (RQ1).
A sensitivity analysis repeats the RQ1 tests without the stand-in sessions.
SDLP, speed variation, workload, usability and trust are compared in the same way (RQ2); these five outcomes form one family and are corrected with the Holm procedure.
All tests use $\alpha = .05$, and effect sizes are reported as $d_z$ with 95\,\% confidence intervals.
For RQ3, two coders classify every failed LLM task by failure type and German-language feature, and agreement on a 20\,\% subset is reported as Cohen's $\kappa$ (RQ3).

The sample size follows an a-priori power analysis in G*Power for a two-tailed paired $t$-test on the primary outcome with $\alpha = .05$, power $= .80$ and $d_z = 0.5$, which yields $N = 34$.
No study yet reports a human--LLM difference in task success, so a medium effect is assumed rather than derived.
The study targets 36 complete datasets, nine per sequence; if only 32 are reached, the detectable effect rises to $d_z = 0.52$.

The main threats to validity are the simulator setting, the single model and a student-heavy sample, which limit generalisation; the latency and speech-recognition differences between conditions, which are measured and reported rather than removed; and wizard skill, which varies because each wizard serves only once and is therefore modelled rather than held constant.

\section{Expected Contributions and Results}

The scientific contribution is the first measurement of how far a tool-using LLM in-car assistant falls short of a human assistant with the same tools, obtained with German-speaking drivers while driving.
A second contribution is a failure taxonomy that separates recognition, understanding, tool and parameter errors and links them to request types and German-language features.

The practical contribution is a reusable German task set and wizard protocol for WorlDrive, together with the human baseline data in the WorlDrive corpus.
From the failure analysis the thesis derives design recommendations for German-language in-car agents.

It is expected that the LLM assistant matches the human on clear requests and falls behind on requests that need a clarifying question, ask for a missing function or contain German compounds and loanwords.
It is further expected that these failures cost extra turns, which should show as higher workload, lower trust and, less certainly, less stable lane keeping.
A null result for clear requests would itself be informative, because it would locate the remaining gap in dialogue management rather than in basic understanding.

The results are limited to one model, a simulator, a mainly student sample and the German language.
The human reference is a briefly trained participant, so it shows what an ordinary co-driver achieves with the same tools, not what an expert operator would.
Without an English comparison condition, the thesis can show which failures co-occur with German features but cannot prove that German causes them.
